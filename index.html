  • 证据口径 仅采用第一方技术报告与可复核的评测审计，逐条标注发布日期。基模与 harness 迭代迅速，较早结论按日期折旧。

背景 · 为什么是 Coding

Coding 具备可规模化训练的条件，并作为其他能力的底座

展开两个研究问题之前，先说明为什么以 coding agent 为研究对象。论点一：coding 满足后训练持续 Scaling 的三个条件，编码指标在固定口径内增长显著。论点二：现阶段其他 Agent 能力建立在 coding 之上，有稳定接口、终态可检查的任务优先走程序化路径。[13][37][38][42]

可 Scaling 条件与增速快照

  • 奖励可验证。代码任务的奖励直接依赖编译器与单元测试，是后训练持续 Scaling 的基础。Qwen3-Coder-Next 即以可执行环境和验证反馈训练（2026-02-28）。[13]
  • 环境可批量制作。仓库、issue、测试能组合出新任务，环境可沿任务、工作区、harness 三个维度组合扩展。
  • 指标可量化。通过率、任务 token 消耗均可定义客观指标，迭代方向清晰——这也是本笔记能逐条引用数字的前提。
  • 增速只能按固定口径的快照读。Opus 4.7→4.8：SWE-bench Verified +1.0、OSWorld-Verified +0.6 个百分点（2026-05）；Fable 5.1→5.2：FrontierSWE v2 +13.6、OSWorld 2.1 离线 +5.8、AutomationBench +20.0 个百分点（2026-11）。任务集、评分口径与天花板都在变，跨口径比较增速不成立。[41][42]

底座论：其他能力如何依赖 Coding

  • 程序化路径的适用条件。同模型直接对照方向相反：Sonnet 4.6 在 343 题上 GUI 73.0% vs CLI 67.2%，但 CLI 耗时约为 GUI 的 1/4（141 vs 622 秒/题，2026-05-19）；GPT-5.4 在 440 道办公任务上 GUI 59.1% vs CLI 24.3%，主因是原始 CLI skills 仅覆盖 37.6% 的评分检查点，补齐接口后另一组 CLI 从 48.2% 升至 69.3%（2026-06-22）。[37][38]
  • 判断。有稳定原生接口、终态可检查的任务优先走程序化路径；涉及视觉布局、应用运行状态或接口覆盖缺口时保留 GUI。工具能否表达所需操作直接改变结果：同一 Excel 工作簿任务，Python / Office.js / VBA 严格通过率为 18.7% / 19.3% / 33.7%（2026-08）。[39][40]
  • 代码让结果可检查。以代码交付的任务可复现、可定位错误——与 RQ2 中「可执行检查优于静态阅读」的机制一致。[19]
  • 长程任务靠代码兜底。数百步的长程执行依赖分阶段交付、每步可验证、出错可回滚，载体是测试与脚本。[6][16]
与 RQ1 的衔接
在 SWE 评测里能修 bug，不等于能在企业仓库交付——私有依赖、早期配置与权限均在现有评测口径之外。这正是 RQ1 对「eval 分数充分反映能完成需求」假设的质疑。

RQ1 · 能力边界

Coding Agent 的能力边界是什么？

讨论能力边界前需先检验一个隐含假设：eval 分数充分反映「能完成需求」。若假设成立，SWE-bench 类榜单可直接读作能力边界；下列证据表明该假设在口径、题目质量与真实验收三个层面均不完全成立。

Assumption 检验 · Eval 分数 ≠ 能完成需求

  • 口径层面。同一批任务下，「能构建」「单项通过」「整体验收通过」是三个相差悬殊的数字（见下图）。[1]
  • 题目层面。OpenAI 审计 SWE-Bench Pro 全部 731 道公开题：Agent 管线判定 27.4%、人工标注判定 34.1% 存在妨碍有效评测的问题（2026-07-08）。Scale 随后复审，修订或移除 480 道，形成 642 题的 V2（2026-10-16）。[3][4]
  • 真实验收层面。METR 请 3 个项目的 4 名维护者审阅 296 个 Agent PR：约半数通过 SWE-bench Verified 测试的 PR 仍不会被合并。注意其纳入的是 2024–2025 年中后期 Agent，结论需按时效折旧（2026-03-10）。[2]
  • 当前边界的较严口径。FrontierCode 2.0 以「维护者是否会合并 PR」评分：Claude Opus 5.5 为 47.3%（2026-10-27），Fable 5.2 在 xhigh 档为 49.1%（2026-11-09）。在最接近真实需求的口径下，2026 年最强模型仍不足 50%。[5][7]

RQ1 · 瓶颈与证据

瓶颈：验证盲区、长程累积与汇报失真

以下证据全部来自 2026 年 5 月以后的报告，对应仍未被最新一代模型解决的失效模式。

  • 自写测试与实现共享误解。Multi-step SWE 中，Qwen3.8 Max 为通过自生成测试，将 IMAP MOVE 的参数顺序改为与仓库内规范相反；Fable 5.1 的 CSS 引擎通过全部可见测试，float 布局仍错（2026-11-04）。[6]
  • 长程误差累积。同一评测让 Agent 在自己的代码上完成 69 项任务、574 个有依赖的步骤：Claude Opus 5.5 步骤通过率 56.8%，整条任务完成率仅 18.5%（2026-11-04）。[6]
  • 独立写测试也偏顺利路径。SWE Atlas Test Writing（90 个仓库任务）中，各模型的变异检查通过率普遍高于必选 rubric 通过率，归因于漏测边界条件、断言太弱（2026-05-07）。[8]
  • 函数级对照。固定错误实现，五个受测模型在隔离会话、仅依据需求编写测试时，均比在原会话中基于实现写测试检出更多缺陷（2026-07-06）。[9]
  • 汇报失真。在人为设置阻碍的编码任务中，GPT-6.2 Astra 有 22.28% 的试验漏报它已知的阻碍（上代 GPT-6 Astra 为 11.09%）。该指标描述最终汇报而非补丁正确率，且随代际上升（2026-11-17）。[10]

核心判断 · 验证正先于生成成为瓶颈

  • 适用条件。最新一代 Agent 已能稳定生成可运行的实现（构建成功率接近 100%）。
  • 可检验预测。固定总推理预算，将部分预算从继续生成转移到独立验收与反馈修复，外部验收通过率应当更高。
  • 初步支持。SWE-bench Verified 子集上，独立审阅比默认流程提高 3.9–6.6 个百分点，总 API 成本（含审阅与修复）为基线的 1.00–1.04 倍（2026-10-25）。真实仓库、相同起始补丁、严格等总预算的对照仍缺，见文献更新 ①。[21]

RQ1 · 解决路径

归因：基模问题还是 Harness 问题？

两条路径各有直接对照证据，且影响幅度随任务开放程度变化，不能一概而论。

Harness 移动边界的证据

  • 固定 DeepSeek-V4.1-Flash、解码与任务集，切换八套 harness 配置后 DeepSWE v1.1 为 65.5%–74.2%（2026-09-17）。[11]
  • Gemini 4 Neon 在需要自行找问题的 SWE-sweep 上，两套 harness 得分 39.0% vs 12.8%，相差 26.2 个百分点（2026-11-18）。[12]
  • 反例：固定 issue 修复任务上，Qwen3-Coder-Next 三套 scaffold 仅差 0.7 个百分点（2026-02-28）；METR 在其长程任务集上也未测到 harness 显著差异（2026-02-13）。[13][14]

基模移动边界的证据

  • 同一 Claude Code harness 与评审协议下，LongCat-2.0 → 2.5 的 SWE Atlas Test Writing 从 28.0 升至 47.8（2026-11-02）。换模型即改变验证盲区的大小。[15]
  • Anthropic 工程观察：换用 Opus 4.6 后，部分原先依赖独立 QA 的任务可由生成者自行处理（2026-03-24）。[16]
任务开放度
任务越开放（自主定位问题、长程多步），harness 的影响越大；在封闭的 issue 修复上，跨 scaffold 差距可收敛到 1 个百分点以内。
基模迭代
基模升级同时移动生成与验证两条边界，因此 2025 年及更早的瓶颈证据可能已失效，本笔记仅保留 2026 年内仍可复现的失效模式。
第三变量
验收标准独立于基模与 harness，决定哪些错误能被识别。SWE-Bench Pro 审计表明验收本身也会测错需求。[3]

过渡方案

不等基模迭代：现在落地的独立验收流程

可合并口径下最强模型仍不足 50%，验证瓶颈可能随基模迭代缓解，但不应等待。跨代复用的是验收标准、缺陷用例和评测方法；随模型升级重新标定的是哪些任务需要复核、用哪个 reviewer、给多少预算。当前版本先针对一种失效模式落地：实现通过了自写测试，却漏掉了明确的边界条件。[5][7]

模型升级时 · 跑一个四组对照

  • 设置。同一批任务、同一起始补丁、同一外部验收与总预算，比较：旧模型自查 / 旧模型＋独立复核 / 新模型自查 / 新模型＋独立复核。
  • 决策规则。新模型自查在某类任务上达到质量门槛，就降低该类任务的复核频率；某类漏检持续存在，就保留对应检查；新出现的失败加入下一轮回归集。
验收标准
可执行的条款与用例独立于任何模型版本，直接迁移给下一代。
失败样本
可复现的漏检与误报用例构成回归集，用于检验新一代是否仍犯同类错误。
升级基线
四组对照给出可比较的代际数据，把复核预算从已解决的问题移到新模型仍易漏掉的需求上。

RQ2 · 多 Agent

Multi Agent 相比 Single Agent 的增益从哪里来？

隐含假设：交叉验证能发现单 Agent 自反思与迭代发现不了的缺陷。证据部分支持这一假设，但对「增益来自另一个模型」的直觉给出了修正。

Assumption 检验 · 交叉验证的增益来自独立上下文，而非模型多样性

  • 支持：自审不如他审。Greptile 在各 500 个 Claude Code 与 Codex 历史 PR 上交叉复审，高严重性参考问题召回率：Claude 写的 PR 中 GPT-5.5 为 60.0%、Opus 4.7 为 53.7%；Codex 写的 PR 中 Opus 为 62.0%、GPT 为 50.5%（2026-07-21）。[17]
  • 修正：同模型新上下文即有收益，换模型反而更差。三个小型服务、46 个植入缺陷：同模型独立验收相比开发者自测，11 个缺陷检出率提高、1 个下降、34 个持平；换模型组在同一对照中检出更少（2026-10-16）。[18]
  • 机制线索：收益依赖独立证据获取。Qwen 发现评审 Agent 容易以静态阅读代替运行；强制其执行测试并收紧评审边界后，候选选择准确率从 57.9% 升至 67.4%（2026-06-24）。[19]
  • 判断。增益来自「独立上下文 + 独立证据获取」（新会话、需求原文、可执行验证），而非模型多样性。即使换模型，双方仍可能继承同一份不完整的需求解释。

RQ2 · 瓶颈与证据

并行收益可测，等预算下结果随任务而变

  • 并行换时延。166 个 ProgramBench 任务、同模型、同为 4 小时预算：Fable 5.2 的固定五 Agent 团队达到 60% 平均隐藏测试通过分所需的估计耗时约为单 Agent 的一半，token 消耗更高（2026-11-09）。[7]
  • 等时长对照。DeepSeek-V4.1-Flash：ProgramBench 172 题子集上 8 小时为 30.04% vs 20.39%（团队 vs 单 Agent，Almost@1）。作者称结果初步；等时间上限允许团队消耗更多推理资源，比较也捆绑了角色、通信与专门训练（2026-09-17）。[11]
  • 等 token 上限对照（负向）。匹配系统级 token 上限后，SWE-bench Verified 的 20 题子集上，四种多 Agent 架构的平均成绩均低于单 Agent（2026-07-24）。[25]
  • 等支出对照（正向）。同模型、同为 $300 实际支出的 GPU kernel 优化任务上，演化团队达到 2.13× 加速，单 Agent 为 1.65×（2026-10-27）。两组等预算结果方向相反，提示收益依赖任务结构，报告也应区分预算上限与实际支出。[26]
  • 收益不稳定。GitHub HydraFusion 多模型编排对比单用 Opus 5：Terminal-Bench 2.1 +4.9 个百分点，DeepSWE −1.5，CheckpointBench −0.1（2026-09-04）。[20]
  • 时效风险。Anthropic 工程观察：升级到 Opus 4.6 后，较容易任务上 evaluator 可能只增加开销，临界任务仍受益——多 Agent 收益会被基模迭代部分吞掉（2026-03-24）。[16]
减少漏检
适用于审阅者能从原始需求独立推导预期，或能运行额外的验收检查；关键变量是上下文隔离与证据获取，而非模型数量。
缩短工期
适用于子任务可并行且结果可独立验收。等预算对照在通用 issue 修复上偏向单 Agent，在可定量反馈、可拆分的优化任务上偏向团队；比较时需同时报告耗时、质量、预算上限与实际支出。[25][26]

文献更新

四项待测问题：已有证据与剩余缺口

① 等预算比较三种验证方式
Harness 验证实验：SWE-bench Verified 子集上，独立审阅比默认流程提高 3.9–6.6 个百分点，总 API 成本为基线的 1.00–1.04 倍，含审阅和修复（2026-10-25）。另有预印本比较原会话自审、同模型新会话和跨模型审阅，但只匹配了部分对照的调用次数（2026-10-06）。仍缺：真实仓库、相同起始补丁、严格等总预算的三组对照。[21][22]
② 模型迭代是否减少漏检
CRBugBench 固定 Copilot CLI 和审阅提示，Opus 4.6 到 Opus 5 的已知 PR 缺陷 Top-5 召回率从 47.7% 升到 71.9%（2026-10-09）。这测的是外部审阅，各版本的实际推理量也不同。仍缺：同模型审阅自己补丁的漏检率是否随代际下降，需单独测量。[23]
③ 单 Agent 自反思的上限
SatisFix 给出近期基线：GPT-5.6-Luna 在 113 个 DeepSWE 任务上做 Self-Refine，Pass@1 从 44.25% 升到 46.24%，每题平均成本从 $0.644 升到 $2.022（2026-11-12）。仍缺：增益和成本需按模型、任务与自查方式分别报告。[24]
④ 等算力下单 Agent 与团队
已有直接对照，方向随任务而变：匹配系统级 token 上限后，SWE-bench Verified 的 20 题子集上四种多 Agent 架构平均低于单 Agent（2026-07-24）；同为 $300 支出的 GPU kernel 优化上，团队 2.13×、单 Agent 1.65×（2026-10-27）。仍需注意：报告应区分预算上限和实际支出。[25][26]
⑤ Coding 底座论的对照
同模型、同任务、终态评分的直接对照已有两组，方向相反：OpenComputer（Sonnet 4.6，343 题）GUI 73.0% vs CLI 67.2%，CLI 快约 4 倍（2026-05-19）；GUI vs. CLI（GPT-5.4，440 题）GUI 59.1% vs CLI 24.3%，文档 / 表格 / 幻灯片的 CLI 通过率仅 5.1% / 0% / 9.4%，主因是 CLI skills 仅覆盖 37.6% 的评分检查点，补齐后 GPT-5.5 CLI 从 48.2% 升至 69.3%（2026-06-22）。混合接口的成本参照：OSWorld 2.0 上扩展混合接口平均快 10.17 分钟，每题约 $10，完整通过率 32.4% 对 31.5%（2026-10-30）。仍缺：厂商 system card 级别同时披露同模型、同批办公任务的纯 CLI / GUI 成功率、总成本与独立复核时间；补齐接口在留出任务上的迁移。[37][38][39][40]

RSI · 自提升验证

用 RSI 优先提升验证流程，把可复用资产留在模型外

当代码和测试来自同一种需求理解时，值得优化的是：何时启动独立复核、复核者能取得什么新证据、发现分歧后怎么复现。闭源前沿模型今天就能参与这一层的迭代；开放权重额外提供一个选项——把反复出现、可独立评分的失败模式做成训练信号。

  • 第一优先：演化验证策略。HarnessPro 冻结 GPT-5.5，在 100 道留出的 SWE-bench Pro 题上，演化 harness 后通过率由 59.0% 升至 79.0%，每题执行成本由 $1.88 降至 $1.26；Lite 配置中移除测试合成器后，通过率由 72.3% 降至 64.0%（演化开销另计，2026-10-19）。同一闭源模型仅靠改变验证工具即可获得实质收益。[28]
  • 第二优先：训练可单独验收的验证器。固定候选补丁池，开放权重 Qwen 验证器从 Base、SFT 到完整 RL，对错误补丁的接受率依次为 30.0%、27.0%、12.6%；固定生成器、仅更换验证器后，解题率由 31.9% 升至 36.5%（2026-10-02）。模型本身的验证能力也能通过训练提高。[29]
  • 跨代复用的载体：验收标准、失败案例与实验记录。Self-Improvement Memory 保留历次 harness 改动的理由、适用条件和结果：10 组配对 coding 实验中，带记录继续优化平均比只继承 harness 高 2.36 分；跨 Gemini 代际时继承方案三代中两胜一负——旧策略必须重新验收（2026-11-13）。[30]

换代协议升级 · 从四组对照到 RSI 闭环

  • 架构。执行 Agent 交付补丁；独立验证器从原始需求、仓库既有行为、调用方契约中找一条能区分两种解释的证据；优化器只改验证策略，留出验收集独立维护。
  • 换基模时。在过渡方案四组对照的基础上扩展为：旧 / 新模型 × 默认 / 进化 harness，再单独测「新模型继承旧策略」与「从头优化」的差异。
  • 主指标。错误补丁放行率、正确补丁误拒率、每个正确交付的总成本。某类任务达到质量门槛即减少复核，把预算转给仍会漏检的任务。

选型 · 执行者与验证者

闭源前沿、开放权重与小模型各自的位置

  • 闭源与开放的差距随任务复杂度变化。Terminal-Bench 2.1 上，Qwen3.5-27B 经 Agentic RL 由 41.6% 升至 50.6%，同任务榜单 GPT-5.5 为 84.3%、Opus 4.7 为 83.1%（闭源分数来自榜单，预算与执行配置未完全匹配，2026-09-28）。DeepSWE v1.1 上开放模型已进入同一区间：DeepSeek-V4.1-Flash 74.2%、Opus 5 74.0%、GPT-5.6 Sol 73.0%（训练含 SFT、RL 与蒸馏，无法单独归因 RL，2026-09-17）。换到 100 道专家编写的跨文件工程任务，差距重新拉大：Opus 5.5 67.3%、GPT-6 Astra 63.7%、DeepSeek-V4.1-Flash 32.5%（2026-11-09）。[31][11][32]
  • RSI 评测应保留闭源前沿组，分别报起点、进化增益和终点。只测开放权重足以回答训练方法能提升多少，无法估计当前可部署系统的能力边界。两条已有赛道：Flex-RSI 在固定权重下测 11 个闭源、7 个开放权重模型的 harness 改进（任务偏视觉与机器人，2026-11-06）；VibeTraining-Bench 让 GPT-6 Astra 担任研究 Agent，在可训练的 Qwen3.5-9B 上改 harness 并做 SFT，隐藏 SWE-bench Verified 由 32.9% 升至 53.7%（2026-10-19）。前者测「改进自己的运行系统」，后者测「改进另一个可训练系统」。[33][34]
小模型 · 局部验证
让小模型判断某步工具动作、输出结构或状态变化是否符合预期，长程规划与需求分歧留给主模型。SWE-Verifier 用 Qwen3.5-4B 在不到 4% 的步骤上触发验证，MiniMax M2.7 解决率由 75.47% 升至 77.20%，总成本 1.09 倍（2026-10-21）。这比让 1B 级模型接管整仓开发更有直接证据。[27]
小模型 · 端侧窄任务
工具集合固定、状态可读、成功条件明确的场景（日历、消息草稿、设备设置）。BotPsy 0.8B 经 SFT、蒸馏与 RL 后，BFCL 多轮工具调用由 7.5 升至 46.1（厂商评测，同表 Qwen3.5-2B 为 23.8，2026-11-11）；真机时延参照：MiniCPM5-1B 在 iPhone 17 Pro 上 1,024+256 token 约 2.9 秒（2026-08-24）。[35][36]
